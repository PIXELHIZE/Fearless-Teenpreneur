# 문제 생성 실패 및 품질 검증 분석

분석 기준: 2026-09-19, 사용자가 제공한 스크린샷과 수정 전 코드.

## 실패 원인

스크린샷의 마지막 메시지는 검증 단계의 `Request timed out.`이다. 기본 설정은 호출당 180초, SDK 자동 재시도 1회였다. 10문항 요청은 여유분 2문항을 포함한 12문항을 한 번에 검증하며 높은 추론 강도, 최대 출력 24,000토큰, 웹 도구 호출 한도 36을 요청했다. 같은 대형 요청이 재시도되면 약 360초 후 실패하므로 관찰된 로그와 일치한다. 20초마다 출력된 메시지는 로컬 타이머이며 서버의 실제 검증 진행을 의미하지 않는다. 정확한 서버 내부 병목은 당시 요청 ID와 API 로그가 없어 확정할 수 없다.

`generated/failures`의 이전 로그에는 예시 API 키로 인한 401 오류도 있었다. 이는 첨부 화면의 검증 타임아웃과는 별도 오류다. `gpt-sol`은 기존 코드에서 `gpt-5.6-sol`로 변환되므로 별칭 자체가 이번 타임아웃의 원인이라는 근거는 없다.

## 기존 품질 검증의 문제

- 같은 호스트의 경로가 접두 관계이면 출처 확인으로 처리했다. 홈페이지 검색만으로 임의의 하위 문서를 승인하거나, 같은 게시판의 서로 다른 문서 식별 쿼리를 혼동할 수 있었다.
- 출처 점수 45 이상이라는 기준은 비공식 사이트도 검색 결과·HTTPS·모델이 적은 발행자와 주장만으로 통과할 수 있었다.
- 초안의 정답과 해설을 검증자에게 그대로 제공했다. 별도 호출이지만 독립 풀이를 강제하지 못했다.
- 문항 전체에 근거 URL 하나만 있으면 통과할 수 있었다. 다섯 선지를 각각 판정했는지, 주장에 연결한 sourceId가 유효한지 확인하지 않았다.
- 중복 검증 ID는 첫 결과만 채택했다. 초안 ID도 모델 출력에 의존했다.
- 검증 중 문구를 바꿔도 기존 근거 주장을 유지했다. 변경된 문항이 새로 검증되었다는 보장이 없었다.
- 자료에 근거한 신규 개념 문제를 만들도록 설계되어 있었으며, 특정 기출 문항을 찾아 변형하는 알고리즘은 아니었다.

## 수정한 동작

1. Responses API 스트리밍과 호출 전체 제한 시간을 적용하고 숨은 SDK 재시도를 제거했다. SDK의 현재 생성 요청 타입에 없는 `max_tool_calls` 요청 필드도 제거했다.
2. 출제는 최대 4문항, 검증은 최대 2문항씩 실행한다. 검증 묶음이 시간 초과되면 1문항씩 재시도하며, 단일 문항도 실패하면 제외하고 보충한다. 통과 결과는 실행 중 유지한다.
3. 출처는 정규화한 URL의 경로·문서 식별 쿼리가 실제 검색 출처와 일치해야 한다. 추적 파라미터와 앵커만 제외한다. HTTPS와 허용 공공·교육기관 도메인도 필수다. 중복 URL·충돌 ID를 제외한다.
4. 감사한 자료의 원리·사실을 새 사례에 적용하도록 출제한다. 감사에서 제외된 사실은 출제 입력에서 제거한다.
5. 정답·해설·근거 주장을 숨겨 독립 풀이를 요청한다. 다섯 선지의 판정 이유와 출처가 모두 있어야 하며, 정답은 하나여야 한다. 독립 풀이와 초안 정답이 다르면 재출제한다.
6. 검증 중 발문·선지 수정, 근거 누락, 중복 판정, 상충 출처, 잘못된 인덱스는 반려한다. 선지별 판정·검증 출처는 해설 JSON에 저장한다.

## 검증 및 한계

회귀 테스트는 스트림 중단과 미완료 응답, 출처 문서 혼동, 블라인드 입력, 선지별 근거와 단일 정답, 검증 분할과 실패 격리, 10문항의 영역별 5:5 배분과 보충을 검사한다. 실제 API 실행 결과는 별도로 확인한다.

URL 확인은 원문 내용의 자동 증명을 의미하지 않는다. 자료의 의미와 정답 타당성은 웹 도구를 사용하는 모델이 판정하며, 같은 모델의 별도 호출이므로 공통 오류가 남을 수 있다. 신뢰 기관의 도메인에도 오래되거나 부적절한 자료가 있을 수 있다. 독창성·난이도·의미상 중복도 완전하게 보장하지 않는다. 기존의 텍스트 개념 문제 범위를 유지했으므로 지문·표·이미지가 필요한 실제 시험 형식 전체를 구현한 것은 아니다.

통과 결과는 메모리에만 보존한다. 프로세스가 종료되면 재개할 수 있는 디스크 체크포인트는 없으며, 전체 시험 생성 시간은 개별 요청의 180초 제한보다 길 수 있다.
